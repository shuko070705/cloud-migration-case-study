## Key Learnings（学んだ知識）

### インフラ・ネットワーク

- CPU、RAM、ストレージ使用率の分析方法
- Scale UpとScale Outの違い
- Load BalancingとAuto Scalingの役割
- VLANによるネットワーク分離
- Single Point of Failure（単一障害点）
- Right-sizingの基本的な考え方

### バックアップ・障害復旧

- バックアップと冗長化の違い
- RTOとRPOの違い
- Full BackupとIncremental Backup
- 3-2-1 Backup Rule
- 別拠点へのバックアップの重要性
- バックアップの取得と復旧能力は異なること

### IT運用管理

- Managed Serviceの役割
- 運用業務の自動化
- Infrastructure as Code（IaC）の基本概念
- クラウドにおける責任分担
- 人件費削減と生産性向上の違い
- 属人化による運用リスク

### クラウド移行

- Monolithic ArchitectureとMicroservicesの違い
- セッション管理とAuto Scalingの関係
- ソフトウェアの互換性と依存関係
- Rehost・Replatform・Refactorの違い

## Consulting Insights（コンサルティング上の気づき）

- リソース使用率が高くても、それだけで性能問題の根本原因を断定することはできない。
- 現在のリソース使用量だけでなく、将来の事業成長を考慮した分析が必要である。
- 現状と経営陣の希望を比較するGap Analysisによって、課題を明確にできる。
- クラウドへの全面移行だけでなく、部分移行やオンプレミス環境の改善も検討する必要がある。
- 運用負担の軽減は、人件費削減だけでなく、サービス品質や生産性の向上につながる可能性がある。
- 技術的に優れた構成であっても、予算や運用体制に適しているとは限らない。
- 確認済みの事実と分析による仮説を区別することが重要である。

## Key Findings（主な調査結果）

| 項目 | 調査結果 |
|---|---|
| Database | ピークCPU使用率95%、RAM使用率90% |
| Application | ピークCPU使用率75%、RAM使用率80% |
| Network | 回線・Firewall・Core Switchの冗長化なし |
| Storage | Backup Serverの使用率70% |
| Disaster Recovery | 別拠点バックアップなし |
| Recovery Time | DBの復旧に4〜6時間 |
| IT Operations | 主要な運用・保守業務が全業務の70% |
| System Improvement | 週12時間、経営陣の希望は週36時間 |
| Cloud Experience | 本番クラウド運用経験者0名 |
| Software | 現行環境への複数の依存関係が存在 |

## Questions & Uncertainties（未解決事項）

- Databaseの性能問題の根本原因
- 将来的なリソース需要
- 正式なRTO・RPO要件
- 自動化による削減可能工数
- ソフトウェアのクラウド互換性
- アプリケーションの改修範囲と費用
- クラウド移行後の運用体制

## Decisions Made（本日の判断）

- 現行インフラ情報をinfrastructure_inventory.mdに集約する。
- 性能、可用性、運用効率、拡張性を今後の主要な評価項目とする。
- Replatformを移行方式の候補として検討する。
- 現段階ではクラウド移行方式やサービスの選定を確定しない。
- 未確認事項については、今後の調査を通じて検証する。

## Reflection（振り返り）

本日は、現行インフラの詳細を把握するために、技術的なヒアリングと分析を行った。

ネットワークやサーバーの使用率、バックアップ体制、IT担当者の業務負担などを調査することで、技術的な課題が企業のサービス品質や事業成長にどのような影響を与えるかを学んだ。

一方で、インフラやクラウドに関する知識が不足しており、適切な質問の作成や技術的な分析を自力で行うことが難しい場面もあった。特に、ソフトウェアの依存関係やクラウド移行方式については、AIによる解説と分析支援を受けながら理解を深めた。

今後は技術知識を学びながら、ヒアリングで得られた情報を企業の課題や経営上の要件に結びつけ、自分で分析・判断できる範囲を広げていきたい。
