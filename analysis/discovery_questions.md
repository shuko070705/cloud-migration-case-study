### 質問の目的

## Q04 — クラウド移行の可能性と懸念点

### 質問

現在オンプレミスで運用されていますが、
クラウドを利用する選択肢はありますか。

また、クラウド移行を妨げている理由や
懸念点についてお聞かせいただけますか。

### 質問の目的

- クラウド移行に対する経営陣の意向を確認する
- 移行を妨げている要因を特定する
- 技術的・経営的な制約条件を把握する

### クライアントの回答

経営陣はクラウド移行に前向きであり、
AWSとAzureを検討候補としている。

ただし、具体的なサービス調査や
費用試算は実施していない。

#### 1. セキュリティ

- 顧客企業の機密情報・個人情報を扱う
- 一部の顧客との契約で国内データ保管が必須
- 現行環境と同等以上のセキュリティを希望

#### 2. コスト

- クラウド利用料の変動に対する懸念
- 顧客数増加に伴う将来的な費用が不明

#### 3. 移行時の制約・希望条件

| 項目 | 希望条件 |
|---|---|
| 計画停止時間 | 最大2時間 |
| 作業時間帯 | 土日・深夜 |
| データ損失 | 不可 |
| 移行期間 | 6〜12か月以内 |

#### 4. 社内の技術力

| スキル | 経験者数 |
|---|---|
| Linux | 3人 |
| ネットワーク | 2人 |
| PostgreSQL | 2人 |
| AWS基礎 | 1人 |
| Azure基礎 | 0人 |
| 本番クラウド運用 | 0人 |

#### 5. 既存システムとの互換性

- オンプレミスを前提としたアプリケーション
- 移行に必要な改修範囲が不明

#### 6. ベンダーロックイン

- 特定のクラウド事業者への依存
- 将来的な料金上昇への懸念
- 他事業者への移行難易度

#### 経営陣の方針

全面的なクラウド移行に限定せず、
部分移行やオンプレミスの改善も検討する。

### 分析・気づき

- クラウド移行を妨げている要因は、
  技術的な実現可能性だけでなく、
  経営判断に必要な情報の不足にもあると考えられる。
- AWS・Azureの経験者が少なく、
  移行後の運用体制や人材育成も検討する必要がある。
- 顧客情報を扱うため、セキュリティと
  データの国内保管を重視する必要がある。
- 経営陣がクラウド移行に前向きであるため、
  複数のインフラ構成を柔軟に提案できる。

### 追加確認事項

- 現在のITインフラの年間運用費用
- クラウド移行に充てられる予算
- 現在のセキュリティ対策と契約上の要件
- 外部の技術支援や人材教育の利用可否

- 将来的な認証取得を考慮した構成が望ましい

### 分析・気づき

- 災害時にも主要業務を復旧できるよう、
  地理的に離れた国内拠点へのデータ保存が必要である。
- 複数のリージョンを利用できるクラウドは、
  災害対策の有力な選択肢となる。
- 災害時の完全無停止運用は必須ではないため、
  復旧要件を満たす範囲で費用を抑えられる可能性がある。
- 現在のDB復旧時間は4〜6時間であり、
  目標の2時間を達成するためには改善が必要である。
- 年間稼働率99.9%以上を達成するためには、
  障害発生頻度と復旧時間の両方を改善する必要がある。
- クラウドを利用する場合でも、責任共有モデルに基づき、
  クライアント側でアクセス権限、アプリケーション、
  データ保護などの安全性を担保する必要がある。
- 可用性・災害復旧・セキュリティの要求水準を
  満たした上で、費用対効果を評価する必要がある。

### 追加確認事項

- 現在の年間稼働率と年間サービス停止時間
- 災害時に優先して復旧すべき業務機能
- サービス停止による経済的損失
- 災害対策に割り当て可能な予算
- 現在のセキュリティ対策と要求水準との差
- 顧客との契約上のセキュリティ要件の詳細
- RTO・RPOの達成状況を検証する方法

## Q14 — 予算・移行期間・その他の制約

### 質問

- コスト削減目標15〜20%の評価基準は何か。
- 移行後の年間運用予算に上限はあるか。
- 顧客増加に伴う運用費用の増加はどの程度許容されるか。
- 移行期間中の並行運用は可能か。
- 外部技術者やコンサルタントの活用は可能か。

### 質問の目的

- 費用評価の基準を明確にする
- 予算上の制約を把握する
- 事業成長に伴う費用増加の許容範囲を確認する
- 移行期間と移行方法の制約を把握する
- 外部支援の活用可能性を確認する

### クライアントの回答

#### 1. コスト削減目標

- 評価期間は5年間
- オンプレミス継続・改善案のTCOを比較基準とする
- 5年間のTCOを15〜20%削減することが目標
- コスト削減は希望条件であり、絶対条件ではない
- 初期移行費用をTCOに含める
- 人件費削減を前提としない

#### 2. 予算

| 項目 | 金額 |
|---|---:|
| 現在の年間運用費用 | 3,300万円 |
| 年間人件費 | 2,250万円 |
| 人件費以外の年間運用費用 | 1,050万円 |
| 移行後の年間運用費用目標（同規模） | 3,300万円以内 |
| 初期移行予算 | 1,000万円 |
| 初期移行予算上限 | 1,500万円 |

- 年間運用費用に絶対的な上限は設定しない
- 合理的な理由があれば費用増加を許容する

#### 3. 事業成長に伴う費用

| 項目 | 現在 | 3年後の目標 |
|---|---:|---:|
| 顧客企業数 | 200社 | 400社 |
| 年間運用費用 | 3,300万円 | 4,125万円以内 |
| IT担当者数 | 3名 | 原則3名 |

- 顧客数が2倍になった場合でも、
  運用費用の増加率を25%以内に抑えることが目標
- 自動化・運用効率化による対応を希望

#### 4. 移行期間・移行方法

| 項目 | 条件 |
|---|---|
| 希望期間 | 6〜9か月 |
| 最大期間 | 12か月 |
| 並行運用期間 | 1〜2か月 |
| 移行方法 | 段階的な移行を希望 |
| 本番切り替え | 休日・深夜 |
| 許容停止時間 | 最大2時間 |
| Rollback Plan | 必須 |

- 並行運用費用は初期移行予算に含める

#### 5. 外部支援

- 外部技術者・コンサルタントの活用は可能
- 外部支援費用は300〜500万円を想定
- 外部支援費用は初期移行予算に含める
- アーキテクチャ設計、セキュリティ設計、
  DB移行、テスト、教育などの支援を想定
- 移行後は可能な限り自社で運用する
  
### 分析・気づき

- 年間運用費3,300万円のうち約68.2%を
  人件費が占めているため、人員削減を前提としない
  コスト削減の難易度は高い。
- 仮に年間運用費を15〜20%削減する場合、
  人件費以外の費用を約47〜63%削減する必要がある。
- 実際の削減目標は5年間のTCOが基準であるため、
  設備更新費用や将来の設備増強費用も含めて
  実現可能性を評価する必要がある。
- 顧客数が100%増加する一方で、運用費用の増加を
  25%以内に抑えることで、費用効率と収益性の
  向上を目指していると考えられる。
- 原則3名のIT担当者で将来の顧客増加に対応するには、
  マネージドサービス、自動化、運用プロセスの
  改善などが有力な選択肢となる。
- 通常の初期移行予算1,000万円から外部支援費用を
  除くと、残りの予算は500〜700万円となる。
- 並行運用は移行リスクを軽減できる一方、
  一時的な費用増加やデータ同期の課題が発生する。
- 長期的な外部専門家への依存を避けるため、
  IT担当者への教育と技術移転が重要となる。

### 追加確認事項

- 並行運用時に想定される技術的・運用上の課題
- 並行運用時のデータ同期方法
- IT担当者のクラウド学習状況と適応力
- IT担当者の教育に確保できる時間
- 外部支援と社内担当者の役割分担
- 初期移行予算における予備費の確保
- 将来的な人件費やライセンス費用の増加見込み

## Q15 — プロジェクトの成功条件

### 質問

- どの目標を達成すればプロジェクトを成功と判断するか。
- 目標の達成状況をいつ、どのように測定するか。
- 一部の目標を達成できなかった場合はどう判断するか。
- 誰が成果を評価・承認するか。
- 自社運用が可能な状態をどのように判断するか。

### 質問の目的

- プロジェクトの成功条件を明確にする
- KPIと受入基準を定義する
- 評価方法と評価時期を確認する
- 評価・承認の責任者を明確にする
- 移行後の運用体制に関する要件を確認する

### クライアントの回答

#### 1. 必須条件（Must）

| 評価項目 | 成功条件 |
|---|---|
| 既存機能 | 主要機能の正常動作 |
| ピーク時の画面応答 | 2秒以内 |
| ピーク時の帳票作成 | 15秒以内 |
| 年間稼働率 | 99.9%以上 |
| DBのRTO | 2時間以内 |
| DBのRPO | 1時間以内 |
| 災害時の主要業務復旧 | 4時間以内 |
| セキュリティ | Q13の必須要件を満たす |
| 移行時のデータ損失 | なし |
| 移行時の停止時間 | 2時間以内 |
| 初期移行費用 | 1,500万円以内 |
| 拡張性 | 顧客400社規模に対応可能 |

#### 2. 希望条件（Should）

| 評価項目 | 成功目標 |
|---|---|
| 5年間のTCO | 15〜20%削減 |
| 年間稼働率 | 99.95%以上 |
| 改善業務時間 | 週36時間 |
| 性能に関する問い合わせ | 月2件以下 |
| 3年後の年間運用費用 | 4,125万円以内 |
| IT担当者数 | 原則3名 |
| 移行期間 | 6〜9か月 |
| 運用体制 | 外部専門家への依存を最小化 |

#### 3. 評価方法・評価時期

| 評価項目 | 評価方法 | 評価時期 |
|---|---|---|
| 既存機能 | 機能・受入テスト | 移行前 |
| 応答時間 | 性能テスト | 移行前・移行後 |
| 拡張性 | 同時接続1,000人の負荷テスト | 移行前 |
| RTO・RPO | 障害復旧テスト | 移行前・定期的 |
| セキュリティ | 設定レビュー・脆弱性診断 | 移行前・定期的 |
| データ整合性 | 移行前後のデータ比較 | 本番切り替え時 |

| 運用負担 | 業務時間の記録 | 移行後3・6か月 |
| 顧客満足度 | 問い合わせ・アンケート | 移行後3・6か月 |
| 年間稼働率 | モニタリング | 移行後12か月 |
| TCO | 予測値と実績値の比較 | 提案時・毎年・5年後 |

#### 4. 目標未達時の判断

- 必須条件が未達の場合は原則として本番移行を承認しない
- 原因調査、改善、再評価を実施する
- 希望条件は他の改善効果とのバランスで判断する
- 移行後に評価する必須条件については、
  事前テストや設計レビューで達成可能性を確認する
- 移行後の目標未達に対しては改善計画を策定する

#### 5. 評価・承認責任者

| 担当者 | 評価範囲 |
|---|---|
| CEO | 最終承認 |
| 財務部門責任者 | 予算・TCO・費用対効果 |
| IT部門責任者 | 技術・性能・可用性 |
| セキュリティ担当者 | セキュリティ・契約要件 |
| 業務部門代表者 | 機能・業務への影響 |
| ITインフラ担当者 | 運用可能性・保守性 |

#### 6. 自社運用の成功条件

- モニタリングと異常検知
- 一般的な障害の調査・復旧
- バックアップの確認・復元
- セキュリティ設定とアクセス権限の管理
- クラウド利用料金の管理
- リソースの構成・容量変更
- 運用手順書の更新

移行後1か月間は外部専門家の支援を受けながら
自社主体で運用し、運用能力を確認する。

高度な技術課題や重大障害については、
外部サポートの継続利用を許容する。

### 分析・気づき

- 今回の案件の目的はクラウド移行そのものではなく、
  システムの改善と事業課題の解決である。
  クラウドはそのための手段の一つである。
- コスト削減よりも、顧客へのサービス品質に直接関わる
  性能・可用性・セキュリティが必須条件として
  重視されている。
- すべての成果が移行直後に現れるわけではないため、
  評価項目に応じて測定時期を設定する必要がある。
- 技術・財務・セキュリティ・業務など、
  複数の部門がそれぞれの責任範囲において
  成果を評価する必要がある。
- 外部専門家の支援終了後も安定した運用を継続できるよう、
  IT担当者への教育、技術移転、運用手順書の整備が重要である。
- プロジェクトの完了だけでなく、
  中長期的な事業価値の実現まで考慮した提案が必要である。

### 追加確認事項

- 性能テストの具体的な測定条件
- 必須条件が未達となった場合の対応手順
- 移行後のKPI測定・管理の責任者
- IT担当者の運用能力を評価する具体的な方法
- 顧客満足度の現状と目標水準
- 外部支援終了後のサポート体制
